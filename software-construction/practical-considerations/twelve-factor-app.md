# Twelve-factor app

## Summary

The twelve-factor app is a methodology for building software-as-a-service applications that are easy to deploy, scale and operate. Its twelve factors cover the codebase, dependencies, configuration, backing services, build and release, processes, port binding, concurrency, disposability, environment parity, logs and admin processes.

### Codebase

One codebase tracked in revision control, many deploys.

This principle states that all deployments of an application (e.g., development, staging, production) should originate from the same source codebase, managed in a version control system like Git.

**Good practice**

- Using a single Git repository for a microservice. A push to the `main` branch automatically triggers a CI/CD pipeline (using tools like GitHub Actions, Jenkins, or GitLab CI) that builds, tests, and deploys the same artifact to different environments.
- Employing a clear branching strategy like GitFlow or Trunk-Based Development to manage changes.

**Bad practice**

- Having separate repositories like `my-app-prod` and `my-app-staging`. This makes it impossible to track changes consistently.
- Manually copying code files to a server via FTP or SCP. This is error-prone and bypasses version control entirely.
- Storing assets generated by the build process (e.g., compiled code, minified JavaScript) in the repository. The repo should only contain the source code.

**Example**

A team develops a web application. The code lives in a single GitHub repository. When a developer pushes a new feature, a GitHub Action runs tests. Upon merging to the `main` branch, a new action builds a Docker container image, tags it with the Git commit hash, pushes it to a registry, and then deploys that *exact same image* to a staging Kubernetes cluster. After manual verification, the same image is promoted to the production cluster.

### Dependencies

Explicitly declare and isolate dependencies.

An application must never rely on system-wide packages being implicitly available. Instead, it must declare all its dependencies completely and exactly via a dependency declaration manifest.

**Good practice**

- Node.js: Using a `package.json` file and running `npm install`. The `node_modules` directory isolates dependencies per project.
- Python: Using a `requirements.txt` or `pyproject.toml` file with pinned versions (e.g., `requests==2.28.1`) and isolating the environment with tools like `venv` or `Poetry`.
- Using Docker containers to provide a fully isolated environment that includes the OS and all system-level dependencies (like image processing libraries).

**Bad practice**

- Expecting a tool like `ffmpeg` or `ImageMagick` to be pre-installed on the production server. Instead, the installation of such tools should be scripted in the `Dockerfile` or a setup script.
- Developing with `requests==2.28.1` locally but only listing `requests` in `requirements.txt`, which might install version `3.0.0` in production and break the application.

**Example:**

A Python/Django application's `Dockerfile` starts from a base Python image, copies the `requirements.txt` file, and then runs `pip install -r requirements.txt`. This ensures that every container built from this Dockerfile has the exact same set of libraries, regardless of where it runs.

### Config

Store config in the environment.

Configuration, anything that varies between deployments (dev, staging, prod), must be stored in environment variables. This strictly separates configuration from the code, preventing secrets from being checked into version control.

**Good practice**

- Using `.env` files for local development (and ensuring `.env` is in your `.gitignore`).
- In production, using the configuration and secret management systems of your hosting platform:
    - Kubernetes `ConfigMaps` and `Secrets`.
    - AWS Parameter Store or Secrets Manager.
    - HashiCorp Vault.
    - Heroku Config Vars.

**Bad Practice**

- Hardcoding API keys, database URLs, or other credentials directly in the code (e.g., `const API_KEY = "..."`). This is a major security risk.
- Committing config files like `database.yml` with production credentials to Git.
- Creating environment-specific config files in the codebase, like `config.production.js`.

**Example**

A Node.js application connects to a database using `const db_url = process.env.DATABASE_URL`.

-

    - Locally: A developer creates a `.env` file with `DATABASE_URL="postgresql://user:pass@localhost:5432/mydb"`.
    - In Production (Kubernetes): The deployment manifest injects `DATABASE_URL` from a Kubernetes Secret, pointing to a managed cloud database like AWS RDS. The code remains identical.

### 4. Backing services

Treat backing services as attached resources.

A backing service is any service the app consumes over the network, such as a database (MySQL, PostgreSQL), message queue (RabbitMQ), or caching system (Redis). The 12-factor app treats these as attached resources, which can be swapped out without code changes.

- Good Practice (good)
    - Connecting to services via URLs or credentials stored in the config (see Factor 3). This allows you to swap a local PostgreSQL Docker container for a managed AWS RDS instance by simply changing an environment variable.
    - Using standardized protocols. For example, if your app uses an S3-compatible API for file storage, you can test locally against a MinIO server and run in production against AWS S3.
- Bad Practice (bad)
    - Writing code that assumes a database is running on `localhost`.
    - Using vendor-specific features that lock you into one type of service, making it difficult to replace.
- Real-World Example: A Java Spring Boot application needs a Redis cache. The connection URL is configured via the environment variable `SPRING_REDIS_URL`. In development, this points to `redis://localhost:6379`. In production, it points to a managed AWS ElastiCache instance. The application code is completely unaware of this difference.

### 5. Build, release, run

Strictly separate build and run stages.

The deployment process must be broken into three distinct stages:

1. Build: Converts the code repo into an executable bundle (an "artifact"). This could be a compiled binary or a Docker image.
2. Release: Takes the artifact from the build stage and combines it with the config for a specific environment. The resulting release is immutable.
3. Run: Launches the release in the target environment, running it as one or more processes.
- Good Practice (good)
    - Using a CI/CD pipeline. The build stage creates a Docker image tagged with a unique ID. The release is a declarative manifest (e.g., a Kubernetes YAML file) that points to that image tag and injects configuration. The run stage is the act of applying that manifest to the cluster (`kubectl apply -f ...`).
    - Every release should have a unique ID. If you need to fix a bug, you create a *new* release and deploy it; you don't modify a running release.
- Bad Practice (bad)
    - SSHing into a production server, running `git pull`, and restarting the process. This mixes the stages and is not repeatable.
    - Making code changes directly on a running server. This bypasses the build and release stages entirely.
- Real-World Example: When a commit is pushed, a Jenkins pipeline builds a Docker image `my-app:1.2.3`. When deploying to production, a tool like Argo CD creates a release by combining this image with production `ConfigMaps`. It then instructs Kubernetes to perform a rolling update, which is the run stage.

### 6. Processes

Execute the app as one or more stateless processes.

The application should execute as a "share-nothing," stateless process. Any data that needs to persist (the "state") must be stored in a stateful backing service, like a database or an object store.

- Good Practice (good)
    - Storing user session data in a central cache like Redis, not in the web server's memory.
    - Storing user-uploaded files in an object store like AWS S3 or Google Cloud Storage, not on the container's local filesystem.
    - This statelessness allows you to achieve concurrency by simply adding more copies of your process.
- Bad Practice (bad)
    - Using "sticky sessions" in a load balancer, where a user is always routed to the same server. This creates a single point of failure and makes scaling difficult.
    - Writing files to the local disk. In a containerized environment like Kubernetes, that disk is ephemeral and will be destroyed when the container restarts.
- Real-World Example: An e-commerce site stores a user's shopping cart in a Redis database, keyed by a session ID. This allows any of the 50 running web server instances to handle the user's request, as they can all access the central Redis store. If one instance crashes, the user's cart is safe.

### 7. Port binding

Export services via port binding.

A 12-factor app is self-contained and does not rely on a webserver being injected into the execution environment at runtime. Instead, it exports its service by binding to a port and listening for incoming requests.

- Good Practice (good)
    - A Node.js Express app that calls `app.listen(process.env.PORT)`.
    - A Java application packaged as a self-executable `.jar` with an embedded server like Tomcat or Jetty.
    - A Python app served by Gunicorn, which binds to a port specified on the command line.
    - Using Docker's `EXPOSE` instruction to declare the port.
- Bad Practice (bad)
    - Writing an application as a classic PHP script that depends on an Apache server with `mod_php` to run it. The application itself should contain the webserver.
- Real-World Example: A Go application is compiled into a single binary. The binary itself starts an HTTP server and listens on the port specified by the `PORT` environment variable. In Kubernetes, a Service object is created to route network traffic to this port on the running containers.

### 8. Concurrency

Scale out via the process model.

Instead of making one large process more powerful (scaling up), 12-factor apps scale out by adding more processes. These processes are designed to be stateless (Factor 6) and share nothing.

- Good Practice (good)
    - Separating your application into different process types. For example:
        - `web` process: Handles incoming HTTP requests.
        - `worker` process: Pulls jobs from a message queue to handle long-running tasks like sending emails or processing videos.
    - You can then scale these process types independently. If traffic spikes, scale `web` from 2 to 20. If the job queue gets long, scale `worker` from 1 to 50.
- Bad Practice (bad)
    - A monolithic process that does everything. When one part of it is slow (e.g., video processing), the whole application slows down.
    - Relying only on vertical scaling (adding more CPU/RAM), which is expensive and has a hard limit.
- Real-World Example: A video-sharing platform runs 10 `web` pods to handle user uploads and browsing. When a video is uploaded, a message is sent to a RabbitMQ queue. A separate set of 50 `worker` pods are constantly pulling from this queue, transcoding videos. The number of `worker` pods can be automatically scaled up or down by a Kubernetes Horizontal Pod Autoscaler based on the queue length.

### 9. Disposability

Maximize robustness with fast startup and graceful shutdown.

Processes should be disposable, meaning they can be started or stopped at a moment's notice. This is essential for scaling, fast deployments, and robustness.

- Good Practice (good)
    - Fast startup: Minimize the work done on startup. For example, don't wait to establish all database connections on boot; do it on the first request.
    - Graceful shutdown: When a process receives a `SIGTERM` signal, it should stop accepting new work, finish its current task, clean up resources (like database connections), and then exit.
- Bad Practice (bad)
    - Long startup times (e.g., a process that takes minutes to become ready) make scaling slow and painful.
    - A process that dies immediately on `SIGTERM`, potentially corrupting data or leaving a job half-finished.
- Real-World Example: A `worker` pod in Kubernetes is processing a 30-second task. A new deployment starts, and Kubernetes sends `SIGTERM` to the old pod. The pod's code catches this signal, stops listening for new jobs, finishes its current task, and exits cleanly. The job queue ensures that if the pod were killed abruptly, the job would be returned to the queue for another worker.

### 10. Dev/prod parity

Keep development, staging, and production as similar as possible.

Bugs and unexpected issues often arise from gaps between environments. The goal is to reduce these gaps to enable continuous delivery and reduce the risk of production-only bugs.

- Good Practice (good)
    - Using the same technologies across all environments: if you use PostgreSQL 15 in production, use PostgreSQL 15 in development (e.g., via Docker).
    - Leveraging containers (Docker) and orchestration scripts (Docker Compose) to ensure the developer's local environment mirrors production as closely as possible.
    - The people, tools, and time gap should be small. A developer should be able to push a change and see it deployed to production quickly.
- Bad Practice (bad)
    - Developing on macOS with SQLite, testing on a staging Windows server with MySQL, and deploying to production on Linux with PostgreSQL. This is a recipe for disaster.
    - Having a long, manual QA and release process that creates a multi-week gap between when code is written and when it is deployed.
- Real-World Example: A team uses Docker Compose to run their application, a PostgreSQL container, and a Redis container on their laptops. The CI pipeline and the production Kubernetes cluster use the *exact same* Docker images. The only difference is the configuration (database URLs, resource limits) which is injected via environment variables.

### 11. Logs

Treat logs as event streams.

A 12-factor app never concerns itself with routing or storing its logs. Instead, it simply writes its time-ordered event stream to standard output (`stdout`). The execution environment is responsible for capturing, collecting, and routing this stream.

- Good Practice (good)
    - Logging to `stdout` and `stderr`.
    - Writing logs in a structured format like JSON, which makes them machine-parseable for searching and analysis.
    - Using a log aggregator like Datadog, Splunk, or an ELK stack (Elasticsearch, Logstash, Kibana) to collect streams from all running processes into a single, centralized location.
- Bad Practice (bad)
    - The application writing logs to a file like `/var/log/app.log`. This is problematic in containerized environments where filesystems are ephemeral.
    - The app trying to manage log rotation, compression, or shipping. This is not the app's concern.
- Real-World Example: A Go application uses a logging library to print JSON-formatted logs to `stdout`. When running in Kubernetes, a daemon like Fluentd runs on every node, captures the `stdout` stream from all containers, and forwards the log events to a central Elasticsearch cluster. Developers can then use a web interface like Kibana to search and analyze logs from the entire system in real-time.

### 12. Admin processes

Run admin/management tasks as one-off processes.

One-off administrative tasks, such as database migrations or running a console (REPL), should be run as a separate process in the same environment as the application.

- Good Practice (good)
    - Shipping admin scripts (e.g., [`manage.py`](http://manage.py)` migrate`) with the application's source code.
    - To run a task, launch a one-off process using the exact same codebase and config as the long-running application processes.
        - Heroku: `heroku run bash`
        - Kubernetes: `kubectl exec -it <pod-name> -- /bin/bash` or running a one-off Kubernetes Job for migrations.
- Bad Practice (bad)
    - SSHing into a production server to run a command. This is not repeatable and can lead to inconsistencies.
    - Running a migration script from your local laptop against the production database. This is dangerous as your local environment and code may differ from production.
- Real-World Example: A Ruby on Rails application deployment pipeline, after successfully deploying the new code, runs a Kubernetes Job. This job uses the new application's Docker image, connects to the same production database, executes `rails db:migrate`, and then terminates. This ensures migrations are run consistently with the correct code version.
